# 第 2 周：结构化输出与四层校验

## 本周目标

第一周已经学会把问题发给模型。本周解决更重要的问题：

> 模型返回的内容，程序怎样判断能不能使用？

学完后，你应该能够把模型输出依次通过四层检查：

```text
模型原始文本
  ↓ 第 1 层：语法校验
能否解析为 JSON/YAML？
  ↓ 第 2 层：结构校验
是否符合 Pydantic/JSON Schema？
  ↓ 第 3 层：契约校验
接口路径、方法、参数是否存在于 OpenAPI？
  ↓ 第 4 层：业务校验
是否违反 CineFlow 业务规则？
  ↓
人工复核后进入测试用例候选区
```

注意最后一句：即使四层都通过，模型生成的用例仍然应该先进入候选区，而不是直接访问生产环境或执行危险操作。

## 本周最终产物

你需要完成一个“模型生成测试用例校验器”，能够：

- 清理 Markdown 代码围栏。
- 解析 JSON 或 YAML。
- 使用 Pydantic 检查字段和类型。
- 使用 OpenAPI 检查路径、方法和参数。
- 使用 CineFlow 规则阻止危险或明显错误的用例。
- 输出每条错误的具体位置和原因。
- 将通过校验的内容保存到候选文件，而不是正式回归目录。

# 第 1 天：理解结构化输出

## 1.1 自然语言为什么不适合程序直接使用

模型回答：

```text
你可以向电影列表接口发送 GET 请求，然后确认状态码是 200。
```

人能看懂，但程序很难可靠地知道：

- 方法在哪里？
- 路径是什么？
- 状态码是多少？
- 有没有查询参数？
- 用例叫什么？

结构化输出把信息放进固定字段：

```yaml
cases:
  - name: 电影列表正常查询
    request:
      method: GET
      path: /api/movies
      params:
        pageNum: 1
        pageSize: 5
    expect:
      status: 200
      code: 0
```

程序现在可以明确读取：

```python
method = case["request"]["method"]
path = case["request"]["path"]
status = case["expect"]["status"]
```

## 1.2 JSON 和 YAML 的区别

同一份内容可以写成 JSON：

```json
{
  "name": "电影列表正常查询",
  "request": {
    "method": "GET",
    "path": "/api/movies"
  },
  "expect": {
    "status": 200,
    "code": 0
  }
}
```

也可以写成 YAML：

```yaml
name: 电影列表正常查询
request:
  method: GET
  path: /api/movies
expect:
  status: 200
  code: 0
```

简单理解：

- JSON 规则更严格，适合 API 通信。
- YAML 更适合人编写配置，但缩进错误很常见。
- 两者都只能保证“语法可解析”，不能保证业务正确。

## 1.3 四种完全不同的错误

### 语法错误

```yaml
request:
 method: GET
    path: /api/movies
```

缩进错误，YAML 可能无法解析。

### 结构错误

```yaml
request:
  method: GET
```

语法能解析，但缺少 `path`。

### 契约错误

```yaml
request:
  method: GET
  path: /api/films
```

结构完整，但 CineFlow 可能根本没有 `/api/films`。

### 业务错误

```yaml
request:
  method: DELETE
  path: /api/orders/1
```

即使 OpenAPI 中存在类似操作，也不能让模型未经确认删除或改变重要数据。

## 1.4 `safe_load` 为什么重要

读取模型生成的 YAML 时使用：

```python
import yaml

data = yaml.safe_load(text)
```

不要使用不安全的任意对象加载方式。模型输出属于外部输入，应当按不可信数据处理。

## 1.5 今天的练习

分别写出下面四个文件，并用 `yaml.safe_load` 读取：

1. 合法的电影列表测试用例。
2. 缩进错误的 YAML。
3. 缺少 `request.path` 的 YAML。
4. 路径写成 `/api/不存在` 的 YAML。

观察：第 3 和第 4 个可能都能成功解析，这说明“能解析”远远不等于“能使用”。

### 第 1 天验收

- [ ] 能解释自然语言输出为什么难以自动执行。
- [ ] 能说出 JSON 与 YAML 的基本区别。
- [ ] 能区分语法、结构、契约和业务错误。
- [ ] 知道模型输出必须当作不可信输入。

# 第 2 天：使用 Pydantic 定义输出模型

## 2.1 Pydantic 是什么

Pydantic 可以理解为一个“数据安检员”。

你告诉它正确数据应该长什么样，它就帮你检查：

- 字段是否存在
- 类型是否正确
- 数值是否在范围内
- 字符串是否符合规则
- 是否出现不允许的多余字段

## 2.2 在自动化工程中声明依赖

`CineFlowAPI` 已经通过 FastAPI 间接使用 Pydantic，但 `CineFlowAutoTest/requirements.txt` 最好显式声明自己直接使用的依赖：

```text
pydantic>=2,<3
```

安装：

```powershell
cd D:\MovieTicketingAndRecommendationSystem\CineFlowAutoTest
python -m pip install "pydantic>=2,<3"
```

> 真正改项目时，应把依赖写入 `requirements.txt` 并统一安装，不能只依赖某台电脑碰巧已有的包。

## 2.3 为 CineFlow YAML 用例建模

从最小结构开始：

```python
from typing import Any, Literal

from pydantic import BaseModel, ConfigDict, Field, field_validator


class RequestSpec(BaseModel):
    model_config = ConfigDict(extra="forbid")

    method: Literal["GET", "POST", "PUT", "PATCH", "DELETE"]
    path: str = Field(min_length=1)
    params: dict[str, Any] | None = None
    json: dict[str, Any] | None = None
    headers: dict[str, str] | None = None

    @field_validator("path")
    @classmethod
    def path_must_start_with_slash(cls, value: str) -> str:
        if not value.startswith("/"):
            raise ValueError("path 必须以 / 开头")
        return value


class ExpectedSpec(BaseModel):
    model_config = ConfigDict(extra="forbid")

    status: int = Field(ge=100, le=599)
    code: int | None = None
    schema_name: str | None = Field(default=None, alias="schema")


class TestCase(BaseModel):
    model_config = ConfigDict(extra="forbid")

    name: str = Field(min_length=1, max_length=100)
    tags: list[str] = Field(default_factory=list)
    request: RequestSpec
    expect: ExpectedSpec


class GeneratedCases(BaseModel):
    model_config = ConfigDict(extra="forbid")

    cases: list[TestCase] = Field(min_length=1, max_length=50)
```

## 2.4 为什么使用 `extra="forbid"`

模型可能生成拼错的字段：

```yaml
expect:
  statues: 200
```

如果允许任意多余字段，`statues` 可能被悄悄忽略。`extra="forbid"` 会明确报错：出现了不允许的字段。

## 2.5 为什么 HTTP 方法使用 Literal

模型可能输出：

```yaml
method: FETCH
```

普通 `str` 会认为它合法，`Literal[...]` 会把它拦截。

## 2.6 验证数据

```python
raw_data = {
    "cases": [
        {
            "name": "电影列表正常查询",
            "request": {
                "method": "GET",
                "path": "/api/movies",
                "params": {"pageNum": 1, "pageSize": 5},
            },
            "expect": {
                "status": 200,
                "code": 0,
            },
        }
    ]
}

validated = GeneratedCases.model_validate(raw_data)
print(validated.cases[0].request.path)
```

故意改错：

```python
raw_data["cases"][0]["request"]["method"] = "FETCH"
```

Pydantic 会抛出 `ValidationError`。

## 2.7 让错误变得可读

```python
from pydantic import ValidationError

try:
    GeneratedCases.model_validate(raw_data)
except ValidationError as exc:
    for error in exc.errors():
        location = ".".join(str(part) for part in error["loc"])
        print(f"位置：{location}")
        print(f"错误：{error['msg']}")
```

你希望看到类似：

```text
位置：cases.0.request.method
错误：Input should be 'GET', 'POST', 'PUT', 'PATCH' or 'DELETE'
```

而不是只有一句“模型输出不合法”。具体位置对排错非常重要。

# 第 3 天：JSON Schema 与 Pydantic 的分工

## 3.1 JSON Schema 是什么

JSON Schema 是描述 JSON 数据结构的一套标准。CineFlow 当前已经使用 `jsonschema` 校验接口响应。

例如订单响应可以规定：

```json
{
  "type": "object",
  "required": ["code", "message", "data"],
  "properties": {
    "code": {"type": "integer"},
    "message": {"type": "string"},
    "data": {"type": ["object", "null"]}
  }
}
```

## 3.2 Pydantic 与 JSON Schema 不冲突

可以这样理解：

```text
Pydantic：更适合 Python 程序内部解析和使用数据
JSON Schema：更适合跨语言契约和接口响应校验
OpenAPI：描述接口路径、方法、参数和请求/响应 Schema
```

CineFlow 当前的 `common/assertions.py` 已经使用：

```python
Draft202012Validator(schema).iter_errors(document)
```

检查真实 API 响应是否符合 `schemas/` 中的定义。

## 3.3 结构正确不代表内容正确

下面数据可能完全符合 Schema：

```json
{
  "id": 999999,
  "name": "不存在的电影",
  "status": "AVAILABLE"
}
```

Schema 只能确认：

- `id` 是整数
- `name` 是字符串
- `status` 是字符串或枚举

它无法自动确认数据库里有没有 `id=999999`。因此还需要业务事实校验。

## 3.4 为生成用例导出 Schema

Pydantic 模型可以生成 JSON Schema：

```python
import json

schema = GeneratedCases.model_json_schema(by_alias=True)
print(json.dumps(schema, ensure_ascii=False, indent=2))
```

它可以用于：

- 给模型说明期望格式
- 保存为契约文件
- 在别的语言中验证
- 对比不同版本结构

## 3.5 校验 CineFlow API 响应

已有的思路：

```python
import json
from pathlib import Path

from jsonschema import Draft202012Validator

schema_path = Path("schemas/movie-list.schema.json")
schema = json.loads(schema_path.read_text(encoding="utf-8"))

response_body = {
    "code": 0,
    "message": "success",
    "data": {}
}

errors = sorted(
    Draft202012Validator(schema).iter_errors(response_body),
    key=lambda item: list(item.path),
)

for error in errors:
    print(list(error.path), error.message)
```

# 第 4 天：使用 OpenAPI 拦截接口幻觉

## 4.1 OpenAPI 是接口说明书

项目根目录已经有：

```text
cineflow-openapi.json
```

它描述：

- 有哪些路径
- 每个路径支持什么 HTTP 方法
- 查询参数有哪些
- 请求体长什么样
- 响应可能有哪些状态码

模型可能生成结构完美的假接口：

```yaml
request:
  method: POST
  path: /api/movies/recommend-by-mood
```

Pydantic 会认为它没问题，因为方法和路径都是合法字符串。OpenAPI 契约校验才能发现路径不存在。

## 4.2 读取 OpenAPI

假设脚本位于 `CineFlowAutoTest/llm/`：

```python
import json
from pathlib import Path

PROJECT_ROOT = Path(__file__).resolve().parents[2]
OPENAPI_PATH = PROJECT_ROOT / "cineflow-openapi.json"

openapi = json.loads(OPENAPI_PATH.read_text(encoding="utf-8"))
paths = openapi["paths"]

print(f"接口路径数量：{len(paths)}")
for path in sorted(paths):
    print(path)
```

## 4.3 检查路径和方法

OpenAPI 可能使用模板路径：

```text
/api/movies/{movie_id}
```

模型可能生成具体路径：

```text
/api/movies/123
```

初学阶段先校验模板路径，要求模型输出 OpenAPI 原始形式：

```python
HTTP_METHODS = {"get", "post", "put", "patch", "delete"}


def validate_operation(openapi: dict, method: str, path: str) -> list[str]:
    errors: list[str] = []
    path_item = openapi.get("paths", {}).get(path)

    if path_item is None:
        return [f"OpenAPI 中不存在路径：{path}"]

    normalized_method = method.lower()
    if normalized_method not in HTTP_METHODS:
        errors.append(f"不支持的 HTTP 方法：{method}")
    elif normalized_method not in path_item:
        errors.append(f"路径 {path} 不支持方法 {method}")

    return errors
```

测试：

```python
print(validate_operation(openapi, "GET", "/api/movies"))
print(validate_operation(openapi, "POST", "/api/movies"))
print(validate_operation(openapi, "GET", "/api/not-exists"))
```

第一条应该通过；后两条应根据真实契约给出错误。

## 4.4 检查查询参数

```python
def allowed_query_parameters(
    openapi: dict,
    method: str,
    path: str,
) -> set[str]:
    path_item = openapi["paths"][path]
    operation = path_item[method.lower()]

    parameters = []
    parameters.extend(path_item.get("parameters", []))
    parameters.extend(operation.get("parameters", []))

    return {
        item["name"]
        for item in parameters
        if item.get("in") == "query" and "name" in item
    }


def validate_query_parameters(
    openapi: dict,
    method: str,
    path: str,
    params: dict | None,
) -> list[str]:
    if not params:
        return []

    allowed = allowed_query_parameters(openapi, method, path)
    unknown = set(params) - allowed
    return [f"未知查询参数：{name}" for name in sorted(unknown)]
```

例如模型把 `pageNum` 幻觉成 `pageNumber`，就会被发现。

## 4.5 不要重复造复杂轮子

OpenAPI 还涉及：

- `$ref`
- 继承与组合
- 请求体 Schema
- 路径参数
- 不同 Content-Type

初学阶段先完成“路径、方法、查询参数”三项。之后可以使用成熟 OpenAPI 工具或逐步扩展，不要一天内手写完整规范解析器。

2. 不存在的路径。
3. 存在的路径配错误方法。
4. 正确路径中放入不存在的查询参数。

# 第 5 天：清理模型输出与失败策略

## 5.1 模型经常多说一句话

你要求只输出 YAML，它仍可能返回：

````text
下面是生成的用例：

```yaml
cases:
  - name: 电影列表
    request:
      method: GET
      path: /api/movies
    expect:
      status: 200
      code: 0
```
````

现有 `strip_fence` 能处理“内容一开始就是代码围栏”的简单情况，但处理不了围栏前还有解释文字等复杂情况。

## 5.2 最佳方法不是无限清洗

处理优先级：

1. 如果服务商支持原生结构化输出，优先使用。
2. Prompt 明确要求只输出 JSON/YAML。
3. 对常见 Markdown 代码围栏进行有限清理。
4. 解析失败时最多进行有限次数的格式修复请求。
5. 仍失败就判定失败，保存原始输出供排查。

不要使用非常宽松的正则“猜”模型想表达什么，否则可能把错误数据修成看似正确的数据。

## 5.3 保留原始输出

错误做法：

```text
模型原始输出 → 清理 → 覆盖原始内容
```

推荐做法：

```text
raw_output       原始输出，只读保存
cleaned_output   清理代码围栏后的内容
parsed_output    解析后的数据
validation       校验结果
```

以后发现校验器有 Bug 时，可以重新分析原始输出。

## 5.4 清理器示例

```python
def strip_markdown_fence(value: str) -> str:
    text = value.strip()
    if not text.startswith("```"):
        return text

    first_newline = text.find("\n")
    if first_newline == -1:
        raise ValueError("代码围栏缺少正文")

    body = text[first_newline + 1:]
    if not body.rstrip().endswith("```"):
        raise ValueError("代码围栏没有闭合")

    return body.rstrip()[:-3].strip()
```

这个版本仍然故意保持严格：围栏前有解释文字就失败。对测试系统来说，明确失败通常比“聪明地猜”更安全。

## 5.5 格式修复请求

第一次解析失败时，可以给模型一次修复机会：

```text
你上一次的输出无法解析。
错误位置：cases.0.request.method
错误原因：method 必须是 GET/POST/PUT/PATCH/DELETE。

只修复格式，不增加、不删除、不改变测试意图。
仅输出修复后的 YAML。
```

修复后必须重新走全部四层校验。不能因为它叫“修复结果”就直接信任。

## 5.6 为什么要限制修复次数

无限修复会造成：

- 无限循环
- Token 浪费
- 费用增长
- 原始测试意图被模型悄悄改变
- 测试任务长时间不结束

建议初期最多修复 1 次，失败后交给人工。

# 第 6 天：业务规则校验

## 6.1 OpenAPI 不知道完整业务规则

OpenAPI 可以告诉你：

```text
POST /api/orders 存在
请求体需要 scheduleId 和 seatIds
```

但它不一定能告诉你：

- 同一个座位不能卖给两个人。
- 支付回调应该幂等。
- 退款后座位应该恢复 `AVAILABLE`。
- 下架电影不能出现在推荐结果。
- 普通用户不能访问管理员接口。
- 模型生成的用例不能直接连接生产数据库。

这些属于业务规则。

## 6.2 给规则编号

不要只写“业务不正确”，应该给规则一个稳定编号：

| 规则编号 | 规则 |
|---|---|
| CF-AUTH-001 | 未登录用户不能访问个人订单 |
| CF-REC-001 | 推荐结果不得包含下架电影 |
| CF-REC-002 | 推荐结果不得包含重复电影 |
| CF-ORDER-001 | 同一座位不得重复售出 |
| CF-ORDER-002 | 重复支付回调不得重复记账 |
| CF-REFUND-001 | 退款后座位恢复 AVAILABLE |
| CF-AI-001 | AI 不得直接执行支付或退款 |
| CF-AI-002 | AI 不得输出密码、JWT 或 API Key |

规则编号的好处：报告、代码和面试描述都能指向同一条规则。

## 6.3 危险操作拦截

初期可以对模型生成的测试用例设置白名单：

```python
SAFE_GENERATED_METHODS = {"GET"}


def validate_generated_case_safety(case: TestCase) -> list[str]:
    errors: list[str] = []

    if case.request.method not in SAFE_GENERATED_METHODS:
        errors.append(
            f"CF-AI-003：模型生成的 {case.request.method} 用例必须人工审批"
        )

    lowered_path = case.request.path.lower()
    sensitive_fragments = ("payment", "refund", "admin")
    if any(fragment in lowered_path for fragment in sensitive_fragments):
        errors.append(
            "CF-AI-004：支付、退款或管理员接口必须人工审批"
        )

    return errors
```

这不是说 POST 永远不能测试，而是说模型生成的写操作不能未经复核自动执行。

## 6.4 推荐结果业务校验

```python
def validate_recommendations(movies: list[dict]) -> list[str]:
    errors: list[str] = []
    ids = [movie["id"] for movie in movies]

    if len(ids) != len(set(ids)):
        errors.append("CF-REC-002：推荐结果包含重复电影")

    for movie in movies:
        if movie.get("status") != "AVAILABLE":
            errors.append(
                f"CF-REC-001：电影 {movie.get('id')} 不是 AVAILABLE"
            )

    return errors
```

如果模型只返回名称，还应查询数据库得到真实 ID、状态、评分和类型，再验证，不能相信模型自己写出的状态。

def generate_and_validate(spec_text: str) -> dict:
    raw_output = call_llm(spec_text)
    save_raw_output(raw_output)

    try:
        cleaned = strip_markdown_fence(raw_output)
        parsed = yaml.safe_load(cleaned)
    except Exception as exc:
        return rejected(layer="syntax", error=str(exc))

    try:
        generated = GeneratedCases.model_validate(parsed)
    except ValidationError as exc:
        return rejected(layer="structure", error=exc.errors())

    errors = []
    for index, case in enumerate(generated.cases):
        errors.extend(validate_case_against_openapi(index, case))
        errors.extend(validate_case_business_rules(index, case))

    if errors:
        return rejected(layer="contract_or_business", error=errors)

    candidate_path = save_candidate(generated)
    return {
        "status": "waiting_for_human_review",
        "candidate_path": str(candidate_path),
    }
```

# 本周自测题

## 题目

2. Pydantic 能否发现 `/api/films` 在 CineFlow 中不存在？

4. 为什么建议使用 `extra="forbid"`？
5. 为什么应该保存模型原始输出？
6. 为什么格式修复之后还要重新执行全部校验？
7. 模型生成一个完全合法的 `POST /api/orders` 用例后，为什么仍不应该立刻执行？
8. 四层校验分别是什么？

## 参考答案

1. 不能。它只代表 YAML 语法能够解析。
2. 一般不能。Pydantic 主要验证数据结构，需要 OpenAPI 契约校验发现假路径。
3. 通常不能。这属于业务规则，需要单独的业务断言。
4. 防止拼错或幻觉字段被悄悄忽略。
5. 便于排错、审计、重放，也能检查清理器是否错误修改了内容。
6. 修复本身也是模型生成结果，仍然不可信，而且可能改变原始意图。
7. 它会修改系统数据，可能产生订单或锁座，必须由人工确认环境、数据和风险。
8. 语法校验、结构校验、OpenAPI 契约校验、业务规则校验。

# 面试表达练习

不要只说：

> 我让大模型生成 YAML，然后执行 pytest。

推荐表达：

> 我将大模型输出视为不可信输入，设计了四层校验流水线。首先使用安全 YAML 解析检查语法，再通过 Pydantic 严格模型检查字段、类型和枚举；随后读取 FastAPI OpenAPI 契约验证路径、HTTP 方法和参数，最后使用业务规则拦截下架电影推荐及未经审批的支付、退款等写操作。自动校验通过的用例只进入候选区，人工确认后才加入正式 pytest 回归，避免模型幻觉直接影响测试环境。

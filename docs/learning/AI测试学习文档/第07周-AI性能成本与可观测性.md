# 第 7 周：AI 性能、Token 成本与可观测性

## 本周目标

前六周主要解决“回答是否正确、是否安全”。现在解决另外三个问题：

1. 用户要等多久？
2. 系统能同时服务多少用户？
3. 每次回答要花多少 Token 和费用？

AI 应用的请求不是单一接口调用。一次 CineFlow AI 问答可能包含：

```text
接收用户请求
→ 生成问题 Embedding
→ 检索知识库
→ 调用模型选择工具
→ 调用 CineFlow API
→ 再次调用模型生成答案
→ 安全检查和结果返回
```

只记录“整个请求用了 4 秒”，不能告诉你到底哪一步慢。第七周的核心是把整条链路拆开测量。

## 本周最终产物

完成一份 CineFlow AI 性能与成本基线，至少包含：

- 首 Token 延迟和完整响应延迟。
- P50、P95、P99。
- 成功率、超时率、限流率。
- 输入、输出和总 Token。
- 单次请求估算成本。
- RAG、Tool、模型各阶段耗时。
- 5、10、20 并发的阶梯测试。
- 超时、429、5xx 和依赖故障测试。
- Trace、结构化日志和脱敏规则。
- 性能基线与告警门槛。

> 本机测试数据只能作为学习基线，不能声称代表生产服务器能力。没有真实执行就不要编造 QPS、延迟或费用数字。

# 第 1 天：理解 AI 性能指标

## 1.1 响应时间不只有一个数字

普通非流式接口：

```text
发送请求 → 等待 → 一次性收到完整响应
```

流式模型接口：

```text
发送请求
→ 等待第一个 Token
→ 持续收到 Token
→ 完成回答
```

所以至少区分：

### TTFT

Time To First Token，首 Token 延迟。

从发送请求到用户看到第一个输出的时间。它影响“系统有没有马上响应”的感受。

### Total Latency

从发送请求到完整回答结束的时间。

### Inter-token Latency

流式输出过程中相邻 Token 的等待时间。

### Tokens Per Second

模型每秒生成多少输出 Token。粗略计算：

```text
输出 Token 数 / 实际生成阶段秒数
```

## 1.2 P50、P95、P99

假设 100 次请求按耗时从快到慢排列：

- P50：大约中间位置，代表典型用户体验。
- P95：95% 请求不超过这个值，反映较慢用户体验。
- P99：99% 请求不超过这个值，反映尾部慢请求。

平均值不能代替百分位数。

例子：

```text
9 次请求都是 1 秒
1 次请求是 21 秒
平均值是 3 秒
```

平均值看起来还能接受，但有用户等待了 21 秒。

## 1.3 吞吐量

常见指标：

- Requests Per Second：每秒完成请求数。
- Tokens Per Second：每秒生成 Token 数。
- 并发数：同一时间正在处理的请求数量。

并发数不等于每秒请求数。

例如 10 个用户每个人等 10 秒才完成，系统同时有 10 个请求，但吞吐量可能仍然不高。

## 1.4 成功率不能只看 HTTP 200

以下响应可能都是 HTTP 200：

```text
合法回答
空回答
模型说“服务繁忙”
工具调用失败后编造答案
JSON 无法解析
业务 code 非 0
```

AI 性能测试中的成功至少要考虑：

- HTTP 成功
- 业务 code 成功
- 模型输出可解析
- 必要工具调用成功
- 没有超时
- 关键业务断言通过

错误响应返回得很快，不代表性能好。

## 1.5 延迟预算

假设目标总延迟不超过 4 秒，可以先分配预算：

```text
网关和认证：100 ms
Embedding：300 ms
检索：200 ms
工具 API：500 ms
模型生成：2500 ms
输出校验：100 ms
预留：300 ms
```

这只是示例，不是 CineFlow 的实测结论。分配预算的价值是：某阶段超标时能明确定位。

## 1.6 性能测试类型

### 基线测试

小负载下得到正常参考值。

### 负载测试

在预期用户量下验证是否满足指标。

### 压力测试

逐步超过预期负载，找到极限和失效方式。

### 突发测试

短时间突然增加请求。

### 稳定性测试

较长时间运行，检查资源泄漏、连接积压和逐渐变慢。

### 第 1 天验收

- [ ] 能区分 TTFT 和完整响应时间。
- [ ] 能解释 P50、P95、P99。
- [ ] 知道并发数不等于吞吐量。
- [ ] 知道 HTTP 200 不一定代表 AI 请求成功。
- [ ] 能区分基线、负载、压力、突发和稳定性测试。

# 第 2 天：为 AI 链路添加计时和 Token 记录

## 2.1 分阶段计时

一次请求至少拆成：

```text
request_total
embedding
retrieval
model_planning
tool_execution
model_generation
output_validation
```

如果没有使用某阶段，就不记录或记为 0，但不能把所有步骤混成一个 `model_time`。

## 2.2 简单计时器

```python
import time
from contextlib import contextmanager
from dataclasses import dataclass, field


@dataclass
class TimingRecorder:
    durations_ms: dict[str, int] = field(default_factory=dict)

    @contextmanager
    def measure(self, name: str):
        started = time.perf_counter()
        try:
            yield
        finally:
            elapsed = round((time.perf_counter() - started) * 1000)
            self.durations_ms[name] = elapsed
```

使用：

```python
timing = TimingRecorder()

with timing.measure("embedding"):
    query_vector = embedding_client.embed(question)

with timing.measure("retrieval"):
    chunks = retriever.search(query_vector, top_k=3)

with timing.measure("model_generation"):
    answer = llm_client.complete(question, chunks)

print(timing.durations_ms)
```

## 2.3 Trace ID

每个用户请求生成一个唯一 Trace ID：

```python
from uuid import uuid4

trace_id = str(uuid4())
```

模型日志、工具日志、后端 API 日志和评测结果都带同一个 Trace ID，才能把一次请求的证据串起来。

## 2.4 Token 记录

模型服务常返回：

```json
{
  "usage": {
    "prompt_tokens": 1200,
    "completion_tokens": 180,
    "total_tokens": 1380
  }
}
```

需要记录：

- 输入 Token
- 输出 Token
- 总 Token
- 缓存 Token，如果服务商提供
- 模型名称
- 调用次数

Agent 一次用户请求可能调用模型两次，不能只记录最后一次。

## 2.5 端到端记录结构

```json
{
  "trace_id": "trace-001",
  "status": "success",
  "model": "实际模型名",
  "prompt_version": "agent-v2",
  "durations_ms": {
    "embedding": 120,
    "retrieval": 15,
    "model_planning": 600,
    "tool_execution": 80,
    "model_generation": 1400,
    "output_validation": 5,
    "total": 2250
  },
  "usage": {
    "prompt_tokens": 1100,
    "completion_tokens": 150,
    "total_tokens": 1250
  },
  "tool_calls": 1,
  "retry_count": 0
}
```

数字只是格式示例，不能当成项目实测结果。

## 2.6 时间为什么对不上

各阶段之和可能小于总时间，因为还包括：

- Python 调度
- JSON 序列化
- 网络建立连接
- 排队
- 日志处理
- 未单独记录的步骤

可以记录：

```text
unattributed = total - 已知阶段之和
```

差距很大时说明还缺少重要计时点。

## 2.7 脱敏

性能日志不需要保存完整 Prompt 和回答。可以保存：

- case_id
- 输入长度
- 输出长度
- Token
- 模型和 Prompt 版本
- 哈希或脱敏摘要

如果必须保存内容，要先移除 Secret、JWT、手机号、邮箱和订单隐私。

### 第 2 天验收

- [ ] 能对 Embedding、检索、Tool 和模型分别计时。
- [ ] 每次请求有唯一 Trace ID。
- [ ] Agent 多次模型调用的 Token 会汇总。
- [ ] 知道阶段耗时之和可能小于总耗时。
- [ ] 性能日志不保存未脱敏敏感内容。

# 第 3 天：设计并发与阶梯负载

## 3.1 先功能正确，再做负载

顺序：

```text
单用户功能测试
→ 单用户性能冒烟
→ 预热
→ 小并发基线
→ 阶梯增加负载
→ 必要时压力与稳定性测试
```

如果单用户就返回错误，直接加到 100 并发没有意义。

## 3.2 AI 测试不能全部打真实付费模型

真实模型压测可能：

- 快速消耗费用
- 触发服务商限流
- 违反服务商使用约束
- 受共享服务波动影响
- 难以重复

建议三层：

### 本地 Mock 模型

固定延迟和固定响应，测试应用自身、并发控制、队列和工具调用。

### 小规模真实模型验证

低并发、有限次数，测量真实 TTFT、生成速度和错误。

### CineFlow API JMeter 测试

继续使用现有 JMeter 对只读业务工具接口做稳定负载。

不要用大量真实模型请求来证明“会压测”。

## 3.3 Mock 模型应该模拟什么

至少支持：

- 固定正常响应
- 可配置延迟
- 流式分块
- 429 限流
- 500/503
- 超时
- 非法 JSON
- 工具调用响应

这样才能稳定验证系统在不同故障下的表现。

## 3.4 阶梯负载示例

```text
阶段 A：1 用户，30 秒，功能与脚本检查
阶段 B：5 用户，2 分钟，预热
阶段 C：10 用户，5 分钟，基线
阶段 D：20 用户，5 分钟，观察拐点
阶段 E：逐步增加，寻找错误率或延迟明显上升位置
```

这些是学习示例，不是正式 SLA。每一档都要固定：

- 模型或 Mock 配置
- Prompt 和知识库版本
- 问题分布
- 测试环境
- Ramp-Up
- 持续时间
- 超时和重试策略

## 3.5 复用 CineFlow 现有 JMeter

当前项目已经提供：

```powershell
cd D:\MovieTicketingAndRecommendationSystem\CineFlowAutoTest
.\performance\run-jmeter.ps1 -Users 10 -RampUp 10 -Duration 60
```

现有计划主要测试电影列表、热门电影、统计和个人推荐等只读接口。AI Agent 调用这些工具时，后端接口性能仍然会影响整体延迟。

JMeter 报告位于：

```text
CineFlowAutoTest/reports/jmeter/时间戳/html/index.html
```

AI 链路的 TTFT、Token 和模型阶段耗时还需要应用自身记录，不能只依赖 JMeter。

## 3.6 测试问题要有真实比例

不要 100% 都问同一个问题。可以设计：

```text
30% 电影查询
20% 推荐
20% 场次查询
10% 座位查询
10% RAG 规则问答
10% 无答案或异常输入
```

比例应该根据目标使用场景说明来源。学习阶段可以标注为“假设流量模型”。

## 3.7 施压端也可能是瓶颈

本机同时运行 JMeter、FastAPI、数据库、Mock 模型时，它们争抢 CPU 和内存。出现变慢时检查：

- JMeter 资源
- Python/FastAPI 资源
- 数据库连接和锁
- 模型服务
- 网络

不要看到延迟升高就直接断定 CineFlow 代码差。

# 第 4 天：超时、重试、限流与降级

## 4.1 超时要分层

一次 Agent 请求可能有多个超时：

```text
Embedding 超时
检索超时
CineFlow 工具超时
模型规划超时
模型生成超时
整个请求总超时
```

总超时必须大于各阶段合理预算，但不能无限等待。

## 4.2 连接超时和读取超时

`requests` 可以分别设置：

```python
response = requests.post(
    url,
    json=payload,
    timeout=(5, 30),
)
```

通常表示：

- 连接最多等 5 秒。
- 建立连接后读取最多等 30 秒。

具体语义以客户端库文档为准。

## 4.3 重试不是越多越好

适合有限重试：

- 暂时网络错误
- 429
- 502、503、504
- 部分超时

通常不重试：

- 400 参数错误
- 401 Key 错误
- 403 权限不足
- 工具被安全策略拒绝

## 4.4 重试风暴

服务已经过载时，大量请求同时立即重试，会让服务更糟。

需要：

- 指数退避
- 随机抖动
- 最大重试次数
- 尊重 `Retry-After`
- 全局并发限制
- 必要时熔断

## 4.5 幂等性

只读查询重试通常风险较低。

写操作重试可能重复执行：

```text
第一次创建订单已成功，但响应丢失
客户端重试
系统又创建一笔订单
```

所以订单使用幂等键。AI Agent 当前不开放写操作，也是为了减少这类风险。

## 4.6 降级策略

依赖失败时，可以：

- 模型不可用：返回明确的暂时不可用提示。
- RAG 不可用：不要假装已经查过规则。
- 推荐工具失败：提供普通电影列表，前提是明确说明。
- 非关键 Judge 失败：保留原始结果，稍后评分。
- 实时场次工具失败：不得使用过期数据冒充当前结果。

降级必须对用户和日志诚实。

## 4.7 故障注入测试

使用 Mock 依赖模拟：

```text
连续两次 429，第三次成功
一直 503
模型 35 秒不响应
工具返回非法 JSON
Embedding 正常但检索超时
生成结束但输出校验失败
```

检查：

- 重试次数是否正确
- 总时间是否超过预算
- 错误是否被分类
- 是否编造成功
- 是否留下 Trace

### 第 4 天验收

- [ ] 会为不同阶段设置合理超时。
- [ ] 知道哪些错误适合重试。
- [ ] 会防止重试风暴。
- [ ] 知道写操作重试需要幂等。
- [ ] 降级时不会把失败伪装成成功。
- [ ] 能使用 Mock 做故障注入。

# 第 5 天：计算 Token 成本与容量

## 5.1 成本基本公式

假设服务商分别按输入和输出 Token 计费：

```text
单次费用 = 输入 Token / 计价单位 × 输入单价
         + 输出 Token / 计价单位 × 输出单价
```

计价单位和价格以实际服务商最新文档为准，不要把示例价格写死成项目事实。

## 5.2 Agent 成本要累加所有调用

一次用户请求可能包含：

```text
Embedding 调用 1 次
规划模型调用 1 次
工具结果回来后生成模型调用 1 次
安全 Judge 调用 1 次
```

单次业务请求总成本是全部阶段之和。

## 5.3 成本记录对象

```python
from dataclasses import dataclass


@dataclass(frozen=True)
class ModelUsage:
    stage: str
    model: str
    input_tokens: int
    output_tokens: int
    estimated_cost: float


def total_cost(usages: list[ModelUsage]) -> float:
    return sum(item.estimated_cost for item in usages)
```

由于价格可能变化，建议同时保存原始 Token 和计算时使用的价格版本。以后可以重新计算。

## 5.4 成本指标

- 平均单次请求成本
- P95 请求成本
- 每个成功任务成本
- 每个业务类别成本
- 每个模型阶段成本
- 因重试浪费的成本
- 因无用工具调用增加的成本

“每个成功任务成本”比“每次调用成本”更真实。如果一个廉价模型经常失败并重试，最终可能更贵。

## 5.5 降低成本的方法

在不损害质量和安全的前提下：

- 缩短重复 System Prompt。
- 只检索必要的 Top-K 文档。
- 裁剪工具返回字段。
- 简单分类使用更小模型。
- 复杂生成使用更强模型。
- 缓存稳定公共问答。
- 减少无用工具调用和重试。
- 限制输出长度。

每次优化后必须重新跑质量、安全和性能评测。

## 5.6 缓存边界

适合缓存：

- 公共电影规则
- 稳定知识库问题
- 相同知识库版本和 Prompt 下的公共回答

谨慎或不应共享缓存：

- 用户个人订单
- 当前座位状态
- 实时场次
- 包含用户身份的推荐
- 不同权限用户的检索结果

缓存 Key 应包含影响结果的版本和身份信息。否则可能造成过期或跨用户泄露。

## 5.7 容量估算

假设只是演示公式：

```text
每天用户请求数 × 平均单次 Token = 每天 Token
每天用户请求数 × 平均单次费用 = 每天估算费用
```

再分别计算高峰时段并发和限流需求。没有真实用户数据时明确标注“假设”。

### 第 5 天验收

- [ ] Agent 成本会累加全部模型阶段。
- [ ] 保存原始 Token 和价格版本。
- [ ] 关注每个成功任务成本。
- [ ] 知道缓存可能造成过期和跨用户泄露。
- [ ] 成本优化后会重新跑质量和安全回归。

# 第 6 天：日志、指标与 Trace

## 6.1 三类可观测数据

### Logs 日志

记录具体事件：

```text
工具调用失败
模型返回非法 JSON
权限策略拒绝
```

### Metrics 指标

聚合数字：

```text
请求量
错误率
P95 延迟
Token 总量
ASR
```

### Traces 链路

记录一次请求经过哪些阶段，以及每阶段耗时和结果。

三者互相配合：指标告诉你“出问题了”，Trace 告诉你“慢在哪一步”，日志提供具体错误证据。

## 6.2 结构化日志

推荐 JSON 日志，而不是拼接长字符串：

```json
{
  "event": "tool_call_finished",
  "trace_id": "trace-001",
  "tool_name": "get_movie_schedules",
  "duration_ms": 82,
  "status": "success",
  "result_count": 2
}
```

不要写：

```text
tool result = 包含所有订单、手机号和 Token 的完整 JSON
```

## 6.3 推荐指标

### 应用

- 请求数
- 成功率
- 错误率
- 并发数
- 队列长度
- 总延迟 P50/P95/P99

### 模型

- TTFT
- 完整生成时间
- 输入/输出 Token
- 模型错误率
- 429 比例
- 重试次数

### RAG

- Embedding 延迟
- 检索延迟
- 空检索率
- Top-K
- 知识库版本

### Agent

- 工具调用次数
- 平均步骤数
- 工具失败率
- 禁止工具拦截数
- 最大步骤终止数

## 6.4 不要把高基数字段乱放进指标标签

用户完整问题、完整回答、订单 ID、Trace ID 每次都不同，不适合作为聚合指标标签，否则会产生大量唯一序列并增加监控负担。

它们更适合进入受控 Trace 或日志。

## 6.5 告警必须可行动

差告警：

```text
AI 好像变慢了。
```

好告警：

```text
最近 10 分钟模型生成阶段 P95 超过 4 秒，且样本数大于 100。
```

告警应包含：

- 指标
- 时间窗口
- 阈值
- 样本量
- 影响范围
- 查看 Trace 的入口

## 6.6 SLI、SLO、SLA

初学理解：

- SLI：实际测量的指标，例如成功率、P95。
- SLO：团队希望达到的目标，例如 99% 请求成功。
- SLA：对外承诺，通常涉及正式责任。

学习项目可以定义练习 SLO，但不要把它描述为真实生产 SLA。

## 6.7 数据保留与隐私

明确：

- 哪些内容记录
- 保存多久
- 谁能查看
- 如何脱敏
- 如何删除
- 是否发送给第三方模型

调试方便不能成为无限保存用户对话的理由。

# 本周自测题

## 题目

1. TTFT 和总响应时间有什么区别？
2. 为什么平均延迟不能代替 P95？
3. HTTP 200 是否一定代表 AI 请求成功？
4. 为什么不建议用大量真实付费模型请求做初期压测？
5. 为什么要记录每个阶段的耗时？
6. 429 时为什么不能所有线程立即无限重试？
7. 一次 Agent 请求的费用如何计算？
8. 为什么缓存个人订单回答可能造成安全问题？
9. Logs、Metrics、Traces 分别解决什么问题？
10. 本机测试结果能否直接声称为生产容量？

## 参考答案

1. TTFT 是看到第一个 Token 的等待时间，总响应时间是完整回答结束时间。
2. 平均值可能隐藏少数非常慢的尾部请求，P95 更能反映较慢用户体验。
3. 不一定，还要检查业务码、结构、工具和关键断言。
4. 费用高、可能触发限流、难重复，也可能违反服务约束；大部分链路可以用 Mock 测。
5. 才能判断瓶颈在 Embedding、检索、工具还是模型生成。
6. 会形成重试风暴，让过载服务更加严重。
7. 累加 Embedding、规划、生成、Judge 等所有调用的输入和输出成本。
8. 缓存 Key 或权限处理错误可能把一个用户的数据返回给另一个用户。
9. 指标发现异常，Trace 定位链路阶段，日志提供具体事件证据。
10. 不能，本机资源竞争和环境差异很大，只能作为学习或同环境对比基线。

# 电影票务与推荐系统自动化测试平台建设大纲

## 1. 项目定位

你可以把这个项目包装成一个面向电影业务系统的自动化测试平台，而不是只写几个单元测试。

项目名称可以写为：

> 电影票务与推荐系统自动化测试平台

它的目标是：围绕电影查询、分类筛选、影院场次、选座购票、订单、评分评论、推荐结果、统计分析等业务模块，建设一套接口自动化、数据校验、回归测试、性能测试、测试报告和大模型辅助分析能力。

当前你的 `MovieAnalysisAPI` 更偏向电影统计分析 API，已有 mapper/service 层测试。如果你后续补充用户、电影、影院、订单、评论、推荐等接口，就可以自然扩展成完整的“电影票务与推荐系统测试平台”。

## 2. 为什么这个项目适合测试开发简历

电影系统天然包含很多适合测试岗位展示能力的场景：

- 功能测试：注册登录、电影查询、类型筛选、电影详情、购票下单、评论评分、推荐展示。
- 接口测试：用户接口、电影接口、订单接口、评论接口、推荐接口、统计分析接口。
- 异常测试：参数为空、非法 ID、重复下单、库存不足、未登录访问、评分越界、评论为空。
- 数据库校验：订单是否入库、座位状态是否更新、评分均值是否变化、评论数量是否正确。
- 自动化测试：使用 pytest + requests 做核心接口回归测试。
- 性能测试：对电影搜索、热门榜单、推荐接口、订单接口做并发压测。
- 缺陷管理：记录 bug、失败用例、修复状态、回归验证结果。
- 大模型增强：生成测试点、生成边界用例、分析失败原因、输出测试报告摘要。

## 3. 推荐技术栈

### 基础版技术栈

- 后端项目：Spring Boot / MyBatis-Plus / MySQL。
- 自动化测试：Python / pytest / requests。
- 用例管理：YAML 或 JSON。
- 数据库校验：pymysql / SQLAlchemy。
- 断言校验：状态码、业务码、响应字段、JSON Schema、数据库结果。
- 测试报告：Allure。
- 接口文档：Swagger / OpenAPI。
- 持续集成：GitLab CI / GitHub Actions / Jenkins。
- 环境部署：Docker / Docker Compose。

### 进阶版技术栈

- 测试平台后端：FastAPI。
- 测试平台前端：Streamlit 或 Vue。
- 性能测试：JMeter。
- UI 自动化：Playwright。
- 大模型接入：OpenAI / DeepSeek / 通义千问等模型 API。
- Agent 框架：CrewAI / LangGraph，可作为简历扩展项，不建议一开始就上。

## 4. 平台整体架构

可以按下面的结构设计：

```text
电影业务系统
  ├─ 用户模块
  ├─ 电影模块
  ├─ 影院场次模块
  ├─ 订单购票模块
  ├─ 评分评论模块
  ├─ 推荐模块
  └─ 统计分析模块

自动化测试平台
  ├─ 用例管理层：YAML / JSON / Excel
  ├─ 请求执行层：pytest + requests
  ├─ 数据准备层：MySQL 初始化、测试数据构造、数据清理
  ├─ 断言校验层：响应断言、JSON Schema、数据库断言、业务规则断言
  ├─ 报告展示层：Allure 报告、失败截图、日志、趋势统计
  ├─ 持续集成层：CI 流水线、Docker 环境、定时回归
  └─ 大模型增强层：生成用例、分析失败、生成报告摘要
```

## 5. 重点测试模块设计

### 5.1 用户与权限模块

测试点：

- 用户注册成功。
- 手机号、用户名、邮箱重复注册。
- 密码为空、密码过短、格式非法。
- 登录成功后返回 token。
- token 过期、token 缺失、token 伪造。
- 普通用户访问管理员接口被拒绝。

自动化价值：

- 可以封装统一登录方法，自动获取 token。
- 后续所有接口测试都可以复用登录态。

### 5.2 电影查询与筛选模块

测试点：

- 查询电影列表。
- 根据类型、地区、年份、评分筛选电影。
- 查询电影详情。
- 查询热门电影榜单。
- 查询不存在的电影 ID。
- 分页参数为空、为负数、超出范围。

适合断言：

- 响应状态码为 200。
- 返回列表不为空。
- 返回字段包含电影名、类型、评分、地区、上映年份。
- 筛选结果必须符合筛选条件。
- 分页数量不能超过 pageSize。

### 5.3 影院、场次与座位模块

测试点：

- 查询影院列表。
- 查询某电影的可选场次。
- 查询场次座位图。
- 已售座位不能再次购买。
- 锁座后座位状态变化。
- 锁座超时后释放座位。

适合展示的测试能力：

- 状态流转测试。
- 数据库前后置校验。
- 并发测试，例如多人同时抢同一座位。

### 5.4 订单购票模块

测试点：

- 创建购票订单。
- 重复提交订单。
- 座位不存在。
- 座位已售。
- 库存不足。
- 订单取消。
- 支付成功回调。
- 支付失败回调。
- 退款。

核心断言：

- 创建订单后订单表新增记录。
- 支付成功后订单状态变为已支付。
- 座位状态变为已售。
- 取消订单后座位释放。
- 重复支付不能生成重复订单。

这是整个简历项目最有价值的模块，因为它能体现业务链路测试、接口自动化、数据库校验和并发问题。

### 5.5 评分评论模块

测试点：

- 用户观影后评分。
- 评分范围 1 到 10。
- 未购票用户是否允许评分。
- 评论内容为空。
- 评论内容过长。
- 删除评论后数量变化。
- 新增评分后电影平均分更新。

适合大模型扩展：

- 生成正常评论、边界评论、异常评论。
- 对接口失败原因进行语义分析。

### 5.6 推荐模块

测试点：

- 新用户冷启动推荐。
- 根据用户评分推荐相似电影。
- 根据电影类型偏好推荐。
- 热门电影兜底推荐。
- 推荐结果不应包含已下架电影。
- 推荐结果不应重复。
- 推荐接口响应时间不能过长。

核心断言：

- 推荐结果数量正确。
- 推荐结果字段完整。
- 推荐电影状态可用。
- 推荐结果与用户偏好存在一定关联。

注意：推荐结果不一定适合做完全固定的断言，可以采用规则断言，例如“数量正确、无重复、状态正常、类型匹配比例达到阈值”。

### 5.7 统计分析模块

结合你当前的 `MovieAnalysisAPI`，可以重点测试：

- 演员 Top50。
- 地区电影数量统计。
- 年份电影数量统计。
- 电影类型分布。
- 评分区间统计。
- 高分电影均值统计。
- 片长统计。
- 年份 Top20 电影。

适合断言：

- 返回数据不为空。
- 数值字段不为负数。
- Top 榜单排序正确。
- 年份、地区、类型等字段不为空。
- 数据库查询结果与接口返回结果一致。

## 7. 用例数据格式示例

可以用 YAML 管理接口用例：

```yaml
- name: 查询电影列表成功
  module: movie
  method: GET
  url: /api/movies
  params:
    pageNum: 1
    pageSize: 10
  headers:
    Authorization: ${token}
  expected:
    status_code: 200
    business_code: 0
    json_path:
      $.data.list: not_empty
      $.data.pageNum: 1

- name: 查询不存在的电影详情
  module: movie
  method: GET
  url: /api/movies/999999
  expected:
    status_code: 404
    business_code: 404
    message_contains: 电影不存在
```

订单链路可以设计成流程用例：

```yaml
name: 用户完整购票流程
steps:
  - name: 登录
    request:
      method: POST
      url: /api/login
      json:
        username: test_user
        password: "123456"
    extract:
      token: $.data.token

  - name: 查询电影场次
    request:
      method: GET
      url: /api/movies/1001/schedules
      headers:
        Authorization: ${token}
    extract:
      schedule_id: $.data[0].id

  - name: 创建订单
    request:
      method: POST
      url: /api/orders
      headers:
        Authorization: ${token}
      json:
        scheduleId: ${schedule_id}
        seatIds: [A01, A02]
    expected:
      status_code: 200
      db_assert:
        sql: "select count(*) from ticket_order where user_id = ${user_id} and schedule_id = ${schedule_id}"
        result: 1
```

## 8. 实现路线

### 第一阶段：接口自动化基础版

目标：先做出可以运行、可以展示报告的版本。

要做的事情：

- 整理电影项目接口清单。
- 确定核心接口：登录、电影查询、详情、榜单、评论、推荐、订单。
- 使用 pytest + requests 编写接口测试。
- 封装基础请求类。
- 封装 token 获取方法。
- 封装统一断言方法。
- 生成 Allure 测试报告。

产出：

- 能一键执行测试。
- 能生成接口测试报告。
- 至少覆盖 20 到 40 条核心接口用例。

### 第二阶段：数据驱动与数据库校验

目标：从“写死测试代码”升级为“平台化用例管理”。

要做的事情：

- 使用 YAML 管理测试用例。
- pytest 读取 YAML 后自动生成测试。
- 支持参数化。
- 支持提取上一个接口返回值。
- 支持数据库前置数据准备。
- 支持数据库断言。
- 支持测试数据清理。

产出：

- 修改 YAML 就能新增接口测试。
- 支持订单、评论、推荐等链路测试。
- 能验证接口返回和数据库状态是否一致。

### 第三阶段：报告、日志与持续集成

目标：让项目更像“自动化测试平台”，不是单纯脚本。

要做的事情：

- 接入 Allure 报告。
- 记录请求 URL、请求参数、响应结果、断言结果。
- 失败时输出错误详情。
- 接入 GitLab CI / GitHub Actions。
- 使用 Docker Compose 启动后端、MySQL、测试执行环境。
- 每次提交后自动执行回归测试。

产出：

- 自动生成测试报告。
- CI 流水线自动执行。
- 简历可以写“结合 CI 实现自动化回归测试”。

### 第四阶段：性能测试与诊断

目标：补齐测试开发项目的性能能力。

要做的事情：

- 使用 JMeter 对电影查询、热门榜单、推荐接口和统计接口进行只读混合压测。
- 设计并发用户模型。
- 统计平均响应时间、P95、错误率、吞吐量。
- 分析慢接口原因，例如 SQL 慢查询、分页过大、推荐计算耗时。

产出：

- 性能压测脚本。
- 性能测试报告。
- 性能瓶颈分析记录。

### 第五阶段：大模型增强

目标：在已有自动化平台基础上接入 LLM，做出简历亮点。

不要一开始就做复杂 Agent。建议先做三个最容易落地的功能：

- 大模型生成测试点。
- 大模型生成 YAML 用例草稿。
- 大模型分析失败原因并生成修复建议。

等这三个功能稳定后，再考虑 CrewAI 或 LangGraph 这类 Agent 编排。

## 9. 大模型接入方案

### 9.1 大模型可以做什么

大模型适合做“辅助”，不适合完全替代测试断言。

适合接入的功能：

- 根据接口文档生成测试点。
- 根据接口参数生成正常、边界、异常用例。
- 根据业务规则补充遗漏场景。
- 将自然语言需求转换成 YAML 测试用例。
- 分析失败用例，归类为接口错误、断言错误、环境错误、数据错误。
- 根据 Allure 报告生成测试总结。
- 根据性能压测结果给出优化建议。

不建议完全交给大模型的内容：

- 核心业务断言。
- 数据库修改。
- 线上环境操作。
- 支付、订单、库存等高风险操作的自动决策。

### 9.2 大模型接入流程

推荐流程：

```text
接口文档 / Swagger / 需求说明 / 数据库表结构
  ↓
提示词模板 Prompt
  ↓
大模型生成测试点或 YAML 用例
  ↓
JSON Schema 校验输出格式
  ↓
人工确认关键业务规则
  ↓
pytest 执行自动化测试
  ↓
Allure 生成测试报告
  ↓
大模型读取失败日志并生成分析建议
```

### 9.3 大模型用例生成模块

输入：

- 接口名称。
- 请求方法。
- URL。
- 请求参数。
- 参数类型。
- 是否必填。
- 业务规则。
- 返回示例。

输出：

- 正向用例。
- 必填参数为空。
- 参数类型错误。
- 边界值。
- 权限异常。
- 数据不存在。
- 重复提交。
- 业务状态异常。

示例提示词思路：

```text
你是测试开发工程师。
请根据下面接口信息生成接口测试用例。
要求：
1. 覆盖正向、异常、边界、权限、数据一致性场景。
2. 输出 YAML 格式。
3. 每条用例包含 name、method、url、headers、params/json、expected。
4. 不要编造不存在的字段。
5. 如果业务规则不明确，在 remark 中说明需要人工确认。
```

### 9.4 大模型失败分析模块

输入：

- 用例名称。
- 请求方法。
- 请求地址。
- 请求参数。
- 实际响应。
- 预期结果。
- 断言失败信息。
- 后端日志片段。
- 数据库校验结果。

输出：

- 失败类型：接口缺陷、测试数据问题、断言写错、环境问题、依赖服务问题。
- 可能原因。
- 建议排查方向。
- 是否需要提 bug。
- 回归验证建议。

失败分析输出示例：

```text
失败类型：业务逻辑缺陷
可能原因：重复购票时接口仍然创建了新订单，缺少座位状态校验或事务控制。
建议：检查订单创建逻辑中是否先校验座位状态，并确认并发情况下是否使用锁或唯一约束。
回归建议：补充重复下单、并发下单、支付后再次下单三个场景。
```

### 9.5 Agent 版本设计

如果你想参考简历里的 Agent 项目，可以设计四个角色：

- 测试规划 Agent：读取需求、接口文档、数据库表结构，生成测试范围和测试点。
- 用例生成 Agent：根据测试点生成 YAML / JSON 测试用例。
- 执行调度 Agent：选择要执行的用例，调用 pytest、JMeter、Allure。
- 结果分析 Agent：读取失败日志、响应结果、数据库断言结果，输出失败分类和修复建议。

整体流程：

```text
测试任务
  ↓
测试规划 Agent
  ↓
用例生成 Agent
  ↓
执行调度 Agent
  ↓
pytest / JMeter / Allure
  ↓
结果分析 Agent
  ↓
测试总结与修复建议
```

简历中可以写“扩展方案”或“增强模块”，但前提是你至少实现其中一两个可演示功能。

## 10. 你需要学习什么

### 第一优先级：自动化测试基础

- HTTP 协议基础：GET、POST、PUT、DELETE、状态码、Header、Cookie、Token。
- RESTful API 设计。
- JSON 数据结构。
- Postman 基础调试。
- pytest：测试函数、fixture、参数化、断言、测试分组。
- requests：发送请求、处理响应、封装客户端。
- YAML / JSON：用例数据管理。
- Allure：测试报告生成。

### 第二优先级：数据库与后端理解

- MySQL 基础 SQL。
- 表关系设计：用户表、电影表、订单表、评论表、评分表、推荐结果表。
- 事务、唯一约束、索引。
- 数据库断言。
- Spring Boot 接口结构。
- MyBatis-Plus 基础。
- 日志排查。

### 第三优先级：测试开发工程化

- Git 基础。
- Maven 基础。
- Docker / Docker Compose。
- GitLab CI / GitHub Actions。
- 环境变量和配置隔离。
- 测试数据初始化和清理。
- 日志收集。

### 第四优先级：性能与稳定性

- JMeter。
- 并发用户模型。
- QPS、TPS、平均响应时间、P95、错误率。
- 慢 SQL 分析。
- 接口超时和重试。
- 并发下单、库存扣减、座位锁定。

### 第五优先级：大模型应用

- Prompt 编写。
- 大模型 API 调用。
- JSON Schema / Pydantic 输出约束。

## 11. 推荐学习顺序

### 第 1 周：把接口测试跑起来

- 学 requests。
- 学 pytest。
- 使用 Postman 调通项目接口。
- 写 5 到 10 条接口测试。
- 生成 Allure 报告。

### 第 2 周：做数据驱动

- 学 YAML。
- 把测试数据从代码里拆出来。
- 封装 APIClient。
- 封装统一断言。
- 支持参数化执行。

### 第 3 周：做数据库校验和业务链路

- 学 pymysql。
- 写数据库查询方法。
- 做订单、评论、评分的数据库断言。
- 做完整购票链路测试。

### 第 4 周：接入 CI 和 Docker

- 学 Docker Compose。
- 把后端、MySQL、测试脚本放到同一套环境里。
- 接入 GitLab CI 或 GitHub Actions。
- 每次提交自动跑测试并生成报告。

### 第 5 周：加入性能测试

- 学 JMeter 线程组、Ramp-Up、断言、非 GUI 执行和 HTML Dashboard。
- 对电影列表、热门榜单、推荐接口、订单接口做压测。
- 输出性能指标和瓶颈分析。

### 第 6 周：接入大模型

- 调用一个大模型 API。
- 输入接口文档，生成测试点。
- 输出 YAML 用例草稿。
- 对 pytest 失败结果做原因分析。
- 生成测试总结报告。

> 电影票务与推荐系统智能化自动测试平台 | 测试开发

> Python / pytest / requests / FastAPI / Allure / MySQL / JMeter / JSON Schema / DeepSeek LLM / CrewAI / Docker

> 面向电影票务、评论评分、推荐结果和统计分析接口，构建自动化测试平台，并接入大模型辅助完成测试点生成、用例编写、失败结果分析和性能诊断建议，形成“规划、生成、执行、分析”的智能化测试闭环。
